### ⏱️ Scene 2: Scalable Ingestion & S3 Presigned URL Flow (1:15 – 2:15)
**Screen**: Switch to `frontend/index.html` and briefly show `lambda/presigned_url/handler.py` and `lambda/csv_processor/handler.py`.

**What to Say**:
> *"Starting with requirement 1: Scalable User Data Ingestion.*
>
> *A standard pattern of uploading 10,000-row CSVs directly through API Gateway into a synchronous Lambda often fails due to the 10MB payload limit and 30-second API Gateway timeouts.*
>
> *Instead, we implemented the industry-standard event-driven S3 Presigned URL pattern:*
> - *The user selects their CSV in our UI.*
> - *The UI calls our API Gateway endpoint `GET /upload-url` to request a presigned S3 PUT URL.*
> - *The frontend uploads the CSV directly to S3.*
> - *S3 automatically triggers our Python `processCsv` Lambda asynchronously.*
> - *The Lambda streams the CSV into Postgres using `execute_values` chunking for maximum throughput and assigns a unique `batch_id` UUID for full idempotency.*
> - *Once stored, Lambda invokes Workflow B via webhook with that `batch_id`."*

### ⏱️ Scene 4: Workflow B — The Optimization Treasure Hunt (3:30 – 5:15)
**Screen**: Switch to n8n canvas showing **Workflow B (Matching Engine)**.

**What to Say**:
> *"Next is Workflow B: User-Loan Matching. This directly addresses the **Optimization Treasure Hunt** creative challenge.*
>
> *The naive approach would be to send every user-product pair to an LLM. But with 10,000 users and 10 loan products, that would require **100,000 LLM calls**. At 0.6 seconds per call, that takes **over 16 hours** and would rack up massive API bills and hit rate limits immediately.*
>
> *To solve this, we designed a **3-stage filtering funnel**:*
>
> *(Click on Node 1: Webhook Trigger)*
> - *Node 1 receives the `batch_id` from the ingestion Lambda.*
>
> *(Click on Node 2: Stage 1 SQL Pre-Filter)*
> - *Stage 1 is our SQL Pre-Filter. PostgreSQL indexes on `monthly_income` and `credit_score` evaluate numeric eligibility across 100,000 candidate combinations in under 50 milliseconds. This immediately discards 95% of unqualified pairs right at the database layer, narrowing 100,000 candidates down to around 5,000.*
>
> *(Click on Node 3: Stage 2 JavaScript Rule Engine)*
> - *Stage 2 is an in-memory Rule Engine running inside an n8n Code node. It performs array matching—checking if the user's employment status matches the loan's allowed employment types array, plus secondary age brackets. This takes less than 100ms and filters the pool down to ~2,000 qualified pairs.*
>
> *(Click on Node 4: Stage 3 Gemini LLM Qualitative Scoring)*
> - *Stage 3 is our LLM integration using Google Gemini. Instead of single calls, we batch 10 qualified pairs per prompt. The LLM performs qualitative assessment—assigning a calculated match score from 0.0 to 1.0 and generating a personalized, human-readable match reason, such as 'Excellent credit score and strong income provide prime eligibility'.*
> - *This reduces LLM calls by **99.8%**, runs in **under 2 minutes**, and costs **$0.00**.*
>
> *(Click on Node 5 & 6: Save Matches & Trigger Workflow C)*
> - *Finally, matches are saved to the `matches` table with `ON CONFLICT DO NOTHING` for idempotency, and an HTTP Request node fires Workflow C's webhook with the `batch_id`."*
